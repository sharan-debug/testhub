## 2. Frontend architecture

React (CRA + craco), React Router v6, Tailwind CSS, Axios, Sonner (toasts), Lucide icons.

**Routing:**

| Path | Component |
|---|---|
| `/login` | Login |
| `/` | Dashboard (protected) |
| `/features` | Features list (protected) |
| `/features/new` | FeatureEdit — create mode (protected) |
| `/features/:id` | FeatureDetails (protected) |
| `/features/:id/edit` | FeatureEdit — edit mode (protected) |
| `/import` | ImportPage (protected) |

**Auth context:** `AuthContext.jsx` calls `GET /api/auth/me` on mount. Sets `user` or `null`. Provides `logout()`.

**API client:** `lib/api.js` — axios instance with `withCredentials: true`. `BACKEND_URL` from `REACT_APP_BACKEND_URL` env var (empty in Docker = same origin via nginx).

**Chat:** `ChatAgent.jsx` — slide-in panel, SSE streaming via `fetch`, session-based history.

**Layout user display:** shows `user.name` and `user.email` (sidebar). Picture shown if present.

**`AuthCallback.jsx`** — unused dead file (leftover from a Google OAuth attempt). Safe to delete.

## 3. Backend architecture

Single file: `backend/server.py` — FastAPI + Motor (async MongoDB) + bcrypt + Anthropic SDK + pandas.

**Framework:** FastAPI, all routes under `/api` prefix via `APIRouter`.

**MongoDB collections currently used:**

| Collection | Purpose |
|---|---|
| `users` | User accounts |
| `user_sessions` | Server-side session tokens |
| `features` | Feature knowledge |
| `activity` | Simplified activity log |
| `chat_messages` | AI chat message history |

**Collections NOT yet created:** `core_features`, `audit_logs`, `imports`.

**Environment variables:**

| Var | Default | Notes |
|---|---|---|
| `MONGO_URL` | required | e.g. `mongodb://mongo:27017` |

## 4. Current MongoDB data models

### users (current)

```python
{
    "user_id": "user_<hex12>",
    "email": "user@example.com",    # used as identity
    "name": "User Name",
    "picture": "",
    "password_hash": "<bcrypt hash>",
    "created_at": "<ISO UTC>"
}
```

**Missing vs V1 DATA_MODEL:** `username`, `role`, `status`, `updated_at`.
**Extra vs V1 DATA_MODEL:** `email`, `picture` (fine to keep, but `username` is the V1 identity).

### user_sessions (current)

```json
{
    "user_id": "...",
    "session_token": "sess_<hex>",
    "expires_at": "<ISO UTC>",
    "created_at": "<ISO UTC>"
}
```

7-day session. Token set as HTTP-only cookie (`secure=False` — dev only).

### features (current)

```python
{
    "id": "feat_<hex12>",
    "name": "...",
    "description": "",
    "owner": "",           # free text, not linked to user _id
    "tags": [],
    "test_data": "",
    "test_steps": "",
    "mocking_steps": "",
    "apis": [
        {
            "method": "GET",
            "path": "",
            "description": "",
            "sample_request": "",

        }
    ],

    "redis_keys": [{"key": "", "description": ""}],
```

The V1 `audit_logs` model requires entity/actor IDs, changed fields, before/after values.

## 5. Current auth flow

1. User submits email + password to `POST /api/auth/register` or `POST /api/auth/login`.
2. Backend bcrypt-verifies (login) or bcrypt-hashes (register).
3. Backend creates a session record in `user_sessions` and sets an HTTP-only cookie.
4. Frontend `GET /api/auth/me` confirms auth state.
5. Logout: `POST /api/auth/logout` deletes session, clears cookie.

**Current identity field:** email address (not username).
**V1 spec identity field:** username.

This is a gap — the docs (AUTHENTICATION.md, DATA_MODEL.md, API_CONTRACT.md) specify username/password, not email/password. The Login UI label says "Email" and the backend model stores email.

## 7. Current import flow

`POST /api/features/import` → parse CSV/XLSX with pandas → immediate insert to MongoDB. No preview, no duplicate detection, no confirmation step.

Supported columns: `name`, `description`, `owner`, `tags`, `test_data`, `test_steps`, `mocking_steps`, `apis`, `mongo_collections`, `redis_keys`, `experiments`.

---

## 8. Current AI/chat flow

1. `POST /api/chat` with `{ "message": "...", "session_id": "..." }`.
2. Backend fetches up to 200 features from MongoDB.
3. Builds a text knowledge context (all feature fields formatted as text).
4. Calls Anthropic API (`claude-haiku-4-5`) via streaming.
5. SSE-streams delta tokens to frontend.
6. Saves user + assistant messages to `chat_messages` collection.

Model is `claude-haiku-4-5` (hardcoded). Company-approved endpoint should be configurable via env var.

## 13. Architectural conflicts and gaps

### Gap 1 — Auth identity: email vs username

**Current:** Uses `email` as the unique user identifier throughout (registration, login, created_by, contributors, etc.).

**V1 spec:** `username` (AUTHENTICATION.md, DATA_MODEL.md, API_CONTRACT.md).

**Impact:** Requires a decision — either migrate to username now (clean V1 alignment) or document email-as-username as an accepted pragmatic choice. Email is more user-friendly for login but contradicts the spec.

**Recommendation:** Keep email as the login field (it is already implemented and familiar). Update docs to reflect this. Do not force a username migration that would break existing data.

### Gap 2 — No roles / RBAC

**Current:** All authenticated users have identical access. No `role` field on the user document.

**V1 spec:** viewer / editor / approver / admin roles, enforced in backend.

**Impact:** Any authenticated user can create, edit, delete, import. No admin user management.

### Gap 3 — No Core Feature

**Current:** No `core_features` collection. Feature form has no Core Feature field.

**V1 spec:** Mandatory Core Feature dropdown.

### Gap 4 — Wrong API storage format

**Current:** APIs stored as `{ method, path, description, sample_request, sample_response }`.

**V1 spec:** `{ curl: "<raw cURL text>", description: "" }`.

**Impact:** Existing data is in the old format. Migration or coexistence strategy needed.

### Gap 5 — Wrong experiment format

**Current:** Experiments stored as generic `{ key: "", description: "" }`.

**V1 spec:** `{ name: "", options: [], required: "" }`.

**Impact:** Existing data is in the old format. Key = experiment name, description = rough notes. Migration needed.

### Gap 6 — Hard delete

**Current:** `DELETE /features/{id}` hard-deletes.

**V1 spec:** Soft delete preferred (status: "deleted").

### Gap 7 — No proper audit log

**Current:** Minimal `activity` collection (no before/after values, no entity type, no changed fields).

**V1 spec:** `audit_logs` collection with full before/after diff.

### Gap 8 — Import is direct (no preview/confirm)

**Current:** CSV upload immediately persists all rows.

**V1 spec:** Upload → parse → preview → confirm → persist + audit event.

### Gap 9 — Search is partial

**Current:** `/features?q=` does regex on name, description, tags only.

**V1 spec:** Dedicated `/search` endpoint covering all fields (Redis keys, experiments, Mongo collections, APIs, etc.) with `matchedFields` in response.

### Gap 10 — No Mark as Verified

**Current:** No `lastVerifiedAt`, `lastVerifiedBy`, no verify endpoint.

**V1 spec:** Simple "Mark as Verified" action.

### Gap 11 — No Jira field

**Current:** No Jira ticket field in feature model or form.

**V1 spec:** Optional Jira field.

### Gap 12 — Cookie security

**Current:** `secure=False` — correct for local dev, but must be `True` for production HTTPS.

### Gap 13 — No MongoDB authentication

**Current:** docker-compose uses unauthenticated MongoDB.

**V1 production spec:** MongoDB should require authentication.
